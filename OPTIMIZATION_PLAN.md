# TechStock shopping performance plan

**Decision for the 25 November 2026 checkout.** Keep the authenticated React → FastAPI shopping path, SQLite/WAL, FTS5, Scrapling adapters and the separate LangGraph/MCP procurement workflow. Start with consistent offer eligibility, database waits that leave the API loop free, and fewer retailer round trips. The audit's warm mouse search is already fast. The largest user-visible opportunities are the wait for a verified card, the empty answer to an overlapping request, and the cost of searching a larger catalog.

This is a plan for future changes. Measurements below come from the [24 November performance audit](PERFORMANCE_AUDIT.md), on `1a75650` **plus its working tree**. The [shopping design](docs/conversational-comparison.md) documents the current request path. The [README](README.md), [verification record](verification.md), [error taxonomy](errors.md) and [threat model](threat_model.md) define existing behavior to preserve. The earlier 108-offer benchmark and procurement-only report use different workloads.

## Targets and measurement boundaries

Use the same machine class, catalog contents, frozen observation age and transport for each before/after pair. Targets are proposed release gates. The cold timings and byte counts in the audit were individual fixture observations. Repetitions specified below establish their distributions. Requests that return an incorrect or empty result cannot pass a speed gate for a known match.

The audit snapshot had 126 non-demo offers, 95 eligible by age and stock alone, and zero cross-retailer identity groups. Two stores appearing anywhere in the results is a coverage measure. A price comparison requires two eligible offers for **the same variant**. Successful live origin and model latency, real browser paint, market-wide recall and sustained throughput need separate baselines. The audit's 33 ms DNS failure and short ASGI bursts are unsuitable production targets.

## Delivery order

| Phase | Priority and dependency | Deliverable and release decision |
|---|---|---|
| 0. Reproduce the audit | First, before changing behavior | Paired benchmark runner, outcome labels and baseline artifact |
| 1. Correct the evidence | After 0 | Shared eligibility, conservative identity and labeled relevance corpus. Later optimizations must preserve these results |
| 2. Scale local retrieval | After 1 | Nonblocking API, fewer rows hydrated, bounded SQLite queries and evidence-aware cache reads |
| 3. Shorten live retrieval | Baseline transport first in 0. Use phase 1 predicates and phase 2 transaction boundaries before rollout | Shared paced transport, retailer route plans, reusable navigation and joined lookups. Enable one source at a time |
| 4. Stream verified changes | After phase 2. Join phase 3 to verify concurrent and cancellation behavior | Bounded progress delivery and responsive conversation UI, with compatible final results |
| 5. Reduce planner cost | Can proceed after 1 using phase 0 provider fixtures | Local routing for unambiguous turns, bounded evidence for the remaining model calls |
| 6. Prove capacity | After enabled paths pass their own gates | Mixed-load and recovery evidence, then a decision on worker count or additional infrastructure |

### Phase 0 — Build the baseline once

Extend `eval/shopping_benchmark.py` beyond repeated direct searches. Add authenticated JSON and streaming profiles at the ASGI boundary, a paced fixture that replaces only the origin transport, and a browser profile. Keep `eval/shopping_eval.py` for simple constraints and add independently labeled cases for quality. Capture the Git revision and working-tree diff fingerprint, runtime and dependency versions, settings, snapshot fingerprint, observation clock, fixture seed and hardware with every result. Use a disposable WAL-consistent backup or a reproducible synthetic equivalent. Use the latter as a new paired baseline if the original snapshot is unavailable. Keep evaluation writes, catalog refresh and real credentials out of the developer database.

Instrument `backend/services/shopping_metrics.py`, `shopping.find_listings`, the transport and the stream writer. Record wall time for routing, model, SQL read/write/lock wait, ranking, queue wait, host spacing, HTTP, parsing, commit, first **nonempty** cached/verified card and final. A product detail page (PDP) counts as useful only after its offer evidence passes validation. Count SQL statements, rows hydrated, bytes, requests by page kind and status, candidates examined, eligible observations, retries, dropped/coalesced previews, missing provider usage, tokens and cost when rates are known. Separate initial local hits, turns fully served locally, shared lookups and verified live hits. Use bounded histograms and low-cardinality dimensions such as retailer, route, cache state and outcome. Exclude messages, URLs, account identifiers and retailer prose from metric labels. Keep authenticated metrics and payload-hiding defaults.

**Exit gate.** Reproduce the baseline result shapes and fault cases, publish denominators and run-to-run spread, and explain material timing differences before using absolute gates. Track empty, partial, blocked, timed-out and fully successful results separately. Retain existing tests and evaluations as compatibility gates.

### Phase 1 — Make an eligible offer mean the same thing everywhere

1. **Normalize observations at ingestion.** Work in `scraping/parser.py`, `normalize.py` and `refresh_catalog.save`. Require an unambiguous, positive TND Decimal price at millime precision. Reject the audit's `-59.900` input. Interpret French negative, on-order and branch-only stock phrases before broad positive matches. Preserve unknown quantity. Map contradictory or ambiguous offer/DOM evidence conservatively and record a rejection reason. Use one timestamp for successful observation and a separate outcome for failed checking. A list-page price guides discovery only. An omission from a sampled page proves nothing about stock.
2. **Centralize shopping criteria.** Resolve product type, model, strict/inclusive price, required/forbidden/soft features, desired sort and intended use once. Reuse the predicate when counting a PDP toward the discovery target, returning local candidates, grouping offers and constructing fresh previews. SQL may prefilter a superset. Final evaluation uses the same rules. Preserve “under 400” versus “up to 400”, parse locale-specific thousands/decimal separators and Arabic-Indic digits, and ask for TND or clarification for foreign currency or genuinely ambiguous amounts. Known negatives require evidence when material, such as “without RGB”. Keep packs, pads and compatibility accessories out of a standalone mouse query.
3. **Keep storage and comparison identities distinct.** Recollection upserts the same retailer offer by canonical URL or retailer/source ID. Preserve the Offer ID referenced by carts, selections and orders. In `price_comparison.py`, guard *every* cross-store match, including checksum-valid GTIN, against conflicting variant evidence such as capacity, GPU, pack size and color. Then consider normalized brand + manufacturer part number with compatible configuration, followed by exact branded model/title with adequate variant evidence. Keep ambiguous pairs separate. Repeated-digit GTINs and retailer-only SKUs cannot establish a global match. Enforce conflict checks for the whole group so a record with missing fields cannot bridge two incompatible variants. Store the match reason and rule version for inspection. Leave order snapshots immutable.
4. **Rank after hard filtering.** Use the cheapest eligible offer as each card's representative. For cheapest sort, order by exact price and a deterministic tie-breaker. For relevance/recommendation, prioritize exact product type/model and requested capabilities, then published use-case evidence and price. Normalize GPU spellings such as “4060Ti” and “4060 Ti”. Unknown tiers remain explicitly unranked for GPU strength. Source access history can inform retrieval scheduling. HTTP success provides no evidence of product quality. Display price differences, timestamps and evidence for the particular offer paying that price.

**Exit gate.** Require zero hard-filter violations and zero false variant merges on held-out fixtures covering valid-GTIN conflicts, packs, wrong-brand headsets, iPads, negated features and strict-price boundaries. For compatible pairs with reliable identifiers, target ≥95% pair recall and ≥99% precision and report counts. Include ID-poor and ambiguous pairs as a separate stratum. Label at least 60 EN/FR/AR shopping queries balanced across exact models, categories, price, negative features, use cases, refinements and genuinely empty results. Freeze graded relevance judgments by group. Target Recall@12 ≥90% on queries with 1–12 known relevant groups, and nDCG@10 ≥0.85 across all nonempty queries. For broad queries, report the fraction of all labeled relevant groups retrieved as a separate uncapped measure. Report each language and missed cases alongside aggregate scores. Require correct abstention on labeled empty/ambiguous cases. Old catalog rows remain readable. Reprocess stored evidence where available without inventing fresh observation times.

### Phase 2 — Remove database waits from the request loop and hydrate fewer rows

**First change.** Move whole synchronous history/cart/lease/read/write transactions called by async shopping endpoints to bounded worker execution. Give each transaction its own SQLAlchemy Session. Keep write locks short and release before model, HTTP or pacing waits. Limit queued writes and measure SQLite busy time. Reserve capacity for foreground reads. Serialize conflicting turns per owner/conversation or use an atomic version check with an explicit retryable conflict, so a slow earlier turn cannot overwrite newer filters. Preserve order transaction isolation and the independent procurement lock. Run the writer-contention test before changing any index.

**Search.** `shopping.search` currently serializes all matched rows before slicing to 12. `title_index.py` already maintains title FTS5 transactionally. Keep FTS for candidate recall and SQLite for exact offer constraints. Profile `EXPLAIN QUERY PLAN`, candidate counts and bytes decoded at 126, 1,260 and 6,300 offers. Try projected columns, indexed brand/category/type, normalized model/features and stock/age/price predicates. Test a selective offer index against the actual join order and measure write cost before retaining it. Extend FTS only for demonstrated missed aliases/model forms. Preserve a recall path for older rows during backfill.

Rank lightweight candidates, group before the top-12 cut, then bulk-load details and **all eligible retailer offers** for winning groups. Keep a deterministic exhaustive implementation in the test harness. A fixed pre-group top-N can hide a valid cheaper offer or a whole group. In `catalog.search_products` and legacy `/catalog`, remove lazy N+1 loads, push supported predicates into SQL and keep quantity/budget semantics, response fields and existing limits. Replace full scans in `explain_empty` with bounded existence/minimum-price queries. Keep the public full catalog endpoint compatible while allowing optional paging for clients that request it.

**Cache layers and invalidation.** Apply these defaults to the first rollout, then tune against measured hit rate, age distribution, retailer traffic and missed eligible offers.

| Layer and key | Lifetime or invalidation | What a hit may serve |
|---|---|---|
| Bounded process LRU for deterministic query normalization, keyed by normalized text, language, vocabulary version and applicable criteria | Clear on parser/vocabulary change. Cache resolved public criteria only for context-free searches | Reuse query work. Resolve owner-specific refinements, cart and ordinals against their own conversation |
| SQLite offers, facets, FTS and optional bounded result-ID cache keyed by canonical criteria, sort, rule version and catalog generation | In the same transaction as each ingest, update, removal or stock demotion, maintain facets/FTS and advance generation. Expire result IDs at the earliest applicable 6 h freshness or 48 h eligibility transition. Invalidate negative results on relevant writes | Re-read price, eligibility, timestamp and coverage on output. Prefer a global generation initially. Add result-ID caching only if phase 2 profiling shows useful reuse |
| Shared robots and navigation metadata by retailer, bot identity, URL and policy version | Reuse the existing 10 min robots and 24 h sitemap limits as ceilings. Start category-route TTL at 1 h, subject to origin directives. Expiry, changed rules, response validators or invalid routes trigger revalidation. Bound stored entries and bytes. The six audit sitemap rows occupied 2.34 MB of JSON. If decoding dominates lookup, index permitted URL slugs as compact candidates at refresh time | Reuse permitted category links or sitemap candidates. Recheck URL permission on each fetch. Navigation hits cannot advance a PDP observation time |
| In-flight URL work and short duplicate-query suppression | Share work while active. Separate terminal no-match, partial and failure records. Initially cap completed ordinary suppression at the existing 90 s, forced at 30 s. Invalidate on relevant catalog/policy change. Host cooldown overrides all callers | Share public observations and work status. Recompute eligibility for each subscriber. An unavailable source never seeds a negative inventory result |

Serve eligible cached cards immediately. A recent ordinary match can finish locally under the existing 6 h default. For 6–48 h data, show its timestamp while attempting permitted revalidation. An explicit refresh prioritizes known PDPs, even on a warm hit, subject to host cooldown and bounded duplicate suppression with an honest status. For same-model comparison, check coverage **per identity** and direct live work to missing or stale stores. Drop offers beyond the eligibility cap. An unverified fallback can retain an eligible recorded observation with its original timestamp. Cart and purchase validations still read authoritative offer rows.

**Dependencies, risks and exit gate.** Introduce additive, versioned SQLite migrations since `create_all` cannot upgrade existing columns. Backfill in resumable batches, dual-read/compare against the old path, verify FTS insert/update/delete and switch reads after parity. Exercise old catalogs, simultaneous ingest/search, changed price, removed stock, policy changes and clock-only expiry. Fence updates by observation time so a slow earlier fetch cannot overwrite a newer price or stock state. Test that rolling back a failed write cannot publish a new cache generation or stream event. Pass warm, scale, SQL-count and contention gates. Reject indexes or caches that increase write contention without delivering a measured gain.

### Phase 3 — Spend each permitted retailer request on a better candidate

**Transport.** `discovery.py` already overlaps retailers. `public_pages.get_page` currently sleeps inside worker threads, and batch spiders use `PacedSession`. Put live discovery, CLI and scheduled refresh behind one identified, bounded transport. Keep Scrapling parsing and validate async session equivalence on saved responses. As a first increment, move pacing to cancellable async waits and run only actual blocking fetch/parse calls in a separate bounded pool. Reuse an identified connection session per origin where the pinned transport supports it. Move to native async fetch only if parity and occupancy benchmarks justify it.

Use a fair bounded queue per host, one active fetch per host initially, with a global cap of two for the two active retailers. Reserve opportunities for interactive jobs while letting scheduled refresh make progress. Coordinate actual request starts, in-flight ownership and cooldowns across processes and both collectors with the existing SQLite host clock and expiring lease. Recheck eligibility to start after waking. Release the DB transaction before sleeping. Charge every call including robots, sitemap, retry and validation to the same clock. Enforce the maximum of configured, robots and existing host floors (10 s SpaceNet, 2 s Scoop). Propagate a monotonic deadline through queue, lock acquisition, connect/read and retries. Start with the existing 95 s per-source and 15 s per-request ceilings, including a fair share of waiting time in the per-source budget. Skip work that cannot fit. A timed-out blocking worker retains its permit until the call actually stops.

| Retailer | Query translation and route choice |
|---|---|
| SpaceNet | Map EN/FR/AR types to French menu/category or manufacturer terms through `shopping_terms.py` and existing seed maps. Prefer a matching brand route for explicit brand requests. A Logitech mouse category covers Logitech only. Use a verified general category or permitted navigation for a generic mouse. Keep the existing floor and disallowed search/controller routes off the plan |
| Scoop | Use its own category/brand/gaming map. Validate the audit's general mouse route against current policy and page type before enabling it. Prefer that route for generic mice. Detect selector drift and fall back to a permitted category or bounded sitemap |
| Other sources | Keep Mytek's existing opt-in CLI scope and stop on a block. Tunisianet collection stays disabled. Toprix remains a design reference. Additional endpoints or feeds need documented access and permitted intended use before activation |

Generate one bounded route plan per source from resolved criteria. For explicit verification, try a known offer URL first. Otherwise use a validated category seed, cached navigation, then permitted sitemap fallback. Missing brand or RGB in a slug lowers priority and does not prove a mismatch. Prefer likely in-budget candidates using listing evidence, reserve PDP attempts for another listing page, and diversify candidates when stock/price hints are incomplete. Start with today's two listing pages, seven distinct PDP attempts, six sitemap files and four accepted results per retailer. Record the stopping reason. In the audit's seven-over-budget-page-one case, the 100 TND page-two mouse must be found **within** this budget. Share URL validation across compatible queries, then apply each query's predicate independently.

**Policy and recovery.** Consolidate the batch path's two robots GETs into one valid decision for the actual bot. Fail closed on unavailable or expired rules. Keep same-origin HTTPS checks and default redirect refusal. A failed link (including a 3xx or category 404) can yield to another already-permitted candidate. PDP 404/410 demotes the existing offer to unknown and invalidates caches. Preserve verified partial results if subsequent work fails. Persist expected adapter coverage, usable PDP count and rejection reasons for that run. HTTP 401/403/429/503 or a challenge stops that source and honors the longer of 300 s and valid Retry-After. Do not retry denial. For isolated transient read/connection failures on idempotent GETs, allow at most one jittered retry within host pacing, attempt and time budgets. Track repeated transport failures, open a per-source cooldown (initially after three consecutive failures), and admit a single paced recovery probe after expiry. Keep scheduled status per retailer/category, including partial success, last useful observation and next permitted attempt. Within the existing background traffic budget, refresh frequently requested categories or changing offers before stable low-demand ones. Keep the 24 h sweep as a backstop, stagger jobs, and revisit only failed categories after cooldown. Measure useful updates per 100 requests and age by category before increasing any refresh frequency.

Observe rights for the intended use as well as the bot's current crawl rules. The audit did not establish blanket reuse or provider-processing permission. Apply source-specific field/use settings for indexing, display and provider input. Keep raw text, arbitrary attributes and disallowed source data out of provider requests. Honor changed policies on cached serving and outbound evidence. Keep optional browser rendering off by default. Before any enabled renderer shares this path, account for its actual requests, enforce host/robots checks including subresources and redirects, and stop on challenges. Slow or blocked sources do not justify expanding access.

**Duplicate requests.** Turn `ShoppingLookup` from an exclusion-only lease into a leader/follower operation for equivalent normalized **public** work. Use an in-process task registry for prompt fan-out and the SQLite lease plus a compact result generation/status for other workers. A cross-worker follower can wait using bounded backoff and read committed offers. Lease ownership tokens, expiry and fenced completion protect against a crashed leader finishing late. Each request owns its answer, permissions, verification labels and conversation writes. Distinguish observations collected during the joined lookup from those completed before the turn began. A subscriber disconnect releases its interest. Cancel queued work when no consumer or scheduled job needs it.

**Exit gate.** Run seeded and unseeded cold fixtures side by side. With no network RTT, eliminating the home GET changes Scoop's request starts from 0/2/4/6 to 0/2/4 s and SpaceNet's from 0/10/20/30 to 0/10/20 s. This explains the proposed latency gain. Also require identical-request and overlapping-budget cases, no duplicate robots/PDP fetches for shared active work, zero host-spacing violations across live and batch callers, no extra request during cooldown, one recovery probe, and useful results from the healthy store when the other fails. Verify the unseeded and denied-robots paths before enabling each adapter.

### Phase 4 — Deliver verified cards progressively without repeating the entire search

Change `shopping.find_listings` to publish committed offer/group changes. Keep a per-turn top-12 view. Coalesce updates arriving within a short window (start at 50 ms), send the first eligible card promptly, and do one authoritative final retrieval. Re-evaluate affected group eligibility, price order and top-12 membership. A removal or price change may promote a previously hidden group. Fall back to a coalesced full retrieval where incremental ordering cannot be proven.

Keep the existing JSON and v1 NDJSON contracts. Add an opt-in compact stream with a version, ordered sequence, stable comparison-group ID, upserts, removed IDs and display order. The final frame carries the complete canonical result even if intermediate frames coalesced. Use a bounded latest-state mailbox per subscriber and a separate guaranteed terminal delivery path. On backpressure, coalesce to a recoverable snapshot at a known sequence. Heartbeats on long idle connections carry no cards. Disconnect or cancellation must detach subscribers, free queues and avoid duplicate final writes. Validate conversation ownership before streaming headers when compatible with the negotiated contract.

In `frontend/src/main.jsx`, apply deltas by group ID and keep the underlying offer ID for cart operations. Release the composer when the final arrives, update the sidebar locally, and reconcile the list independently. An ancillary refresh failure must not append a false shopping retry or clear a valid session. Add a client-generated turn ID and an owner-scoped unique write key so retrying a disconnected submission reuses the committed reply. Abort or sequence superseded conversation loads. Serialize rapid mutations to the same cart line. Render recent history first with older pages on demand. Keep EN/FR/AR, RTL layout, offer timestamps and per-turn verification visible.

**Exit gate.** Pass the byte, first-card and DOM gates. Check fragmented multibyte NDJSON, zero/one/multiple results, cheaper offer replacing the representative, removal/reordering, slow consumer, terminal error, disconnect and sidebar failure. Reconstructed final outputs must match JSON/v1 on equivalent input and frozen observations, apart from request-local timings and IDs. Test through a real buffering proxy and production browser before claiming a paint improvement.

### Phase 5 — Pay the model only for turns that need interpretation

Extend `shopping.plan_turn`, `shopping_intent.py` and `shopping_terms.py` around the phase 1 criteria. Recognize high-confidence generic laptop, Bluetooth headset, brand/type, price comparison and multilingual ordinal/refinement requests locally. Include “least expensive”, “le moins cher”, written second-item cart commands and general questions containing “total”. Bind ordinals to the owner's displayed order. A topic switch resets old filters. An ambiguous reference can ask one focused question. Keep general conversation, open-ended categories and the existing one-decision provider path available.

In `shopping_agent.choose_tool`, trim inputs by relevance and a total budget. Send resolved filters, the minimum relevant recent utterances and position-indexed typed facts only when the selected tools need them. Keep position mapping stable when truncating. Exclude raw retailer descriptions, arbitrary specification maps, restricted evidence and unrelated cards. Reuse tool bindings where safe and omit irrelevant schemas only on routes that can still express every valid action. Budget total serialized bytes, estimated model tokens and generated tokens independently, and record actual usage when reported. Bound the model deadline, retain zero automatic SDK retries and local fallback, and use a brief provider cooldown on repeated transient failures. Select the deadline from successful opt-in latency samples. Validate comparison positions and generate merchant price/stock/link claims from retrieved evidence in code.

**Exit gate.** Replay the same labeled turn mix before/after against a counting mock with deterministic outputs. Require ≥50% fewer calls on a frozen mixed suite containing both previously model-routed and still-ambiguous turns, no loss on labeled intent/criteria and correct grounding on every price/stock/link case. Preserve the zero-call fast path and one-call ceiling. Enforce the 12 KiB full-history gate. For a fixed opt-in provider/model sample with reported usage, target ≥30% fewer input tokens per resolved turn with equal task success. Report successful-call p50/p95, failures, fallback times, input/output tokens and unknown usage separately. Keep this last target provisional until a successful paired baseline exists.

Distinguish fast structural gates (SQL count, calls, bytes, host starts, labeled correctness) from timing gates on a dedicated runner. Save anonymized before/after summaries with failures and sample sizes. Compare p95 across repeated runs, investigate variance on a repeat, and block promotion for a reproducible miss. Monitor per-retailer parse yield, time since last valid PDP and cooldown reason. As initial operational alerts, flag zero accepted parses over 20 successfully fetched **expected-product** pages or a retailer missing two scheduled collection intervals. Treat “no matching product for this query” separately from a parser outage.

Roll out by flag for each new reader, transport adapter, stream version and planner route. Shadow local ranking on the same committed observations, then canary a single retailer or small traffic share. A rollback switches readers, routing or stream negotiation back while keeping additive schema and stable IDs. Shadow mode must reuse captured responses so it cannot double retailer traffic. Retain corrected eligibility and policy checks during rollback.

**Operational risks and rollback signals.** A false merge or hard-filter leak blocks promotion even when ranking gets faster. A stale cache hit triggers a return to authoritative SQL reads. A route yielding fewer valid PDPs at equal traffic falls back to the last validated adapter route. A divergent stream final falls back to v1 snapshots. A local planner route that loses a filter returns to the validated planner path. Monitor these signals per language and retailer so an aggregate gain cannot hide a broken segment.

**Scaling decision.** Keep one API worker until phase 6 shows a second improves user-visible latency under the same retailer budget and preserves the graph/MCP ownership and ordering guarantees across workers. Document the highest sustainable concurrency and throughput at the passing mix. If pacing dominates, improve route yield or permitted refresh scheduling. If serialized writes still dominate after phase 2, evaluate separating the collector process or migrating the database against that specific trace. Consider a shared queue/cache or external search engine only when measurements show cross-host coordination or indexed retrieval is the limiting component. Each added service needs a paired benchmark, an operational owner and a rollback path.
